# AgentLab 产品设计草案

2026-10-08 · v0.1 设计提案 · 尚未实现或经用户测试

## 1. 产品主张

**一个能动手改变 Agent 行为、并用执行证据检验结果的交互式实验室。**

用户在这里完成一件完整的事：提出问题，运行 Agent，检查证据，修改配置或状态，再用新的运行验证判断。初学者有解释和引导，开发者可以直接检查原始数据，两者操作的是同一个实验。

长期主线保留原讨论的四个词：可观察、可理解、可复现、可比较。“可复现”需要具体说明：历史记录可以准确回看；固定工具数据可以重复使用；真实模型重新执行仍可能得到不同输出。

### 已知意图与本次建议

| 状态 | 内容 |
| --- | --- |
| 用户已明确表达 | 对执行过程可视化感兴趣；学习与开发方向都可以包含；认可全面扩展和长期成长的潜力 |
| 原对话中的设想 | 六模块、统一 runtime、Time Machine、Battle Arena、Failure Lab、开源和 SDK |
| 本次推荐 | 先验证引导式故障实验；统一实验/记录协议；用一个可控适配器支撑首版 |
| 尚未决定 | 最终名称、公开部署方式、预算、首个模型提供商、长期商业模式、维护人力 |

工作假设是先按个人可维护、中文优先、便于开源的规模设计。这些假设可调整，不代表用户已经选择了技术栈或交付日期。

## 2. 用户与使用场景

| 用户 | 带来的问题 | 第一次使用应得到什么 |
| --- | --- | --- |
| 刚接触 Agent 的学习者 | 模型什么时候调用工具？为什么拿到结果还会出错？ | 能把一次运行中的请求、工具调用、观察和回答对应起来 |
| AI 应用开发者 | 一次运行失败了，改哪里、如何确认修好了？ | 定位证据，创建变体，比较输出、过程和资源消耗 |
| 实验与研究用户 | 哪个策略在同一任务集合下更稳健？ | 固定实验条件、保留版本和重复结果、查看个例与汇总 |

首版优先服务前两类。研究级批量实验在核心记录和评测口径稳定后扩展。

## 3. 六个模块如何成为一个产品

核心对象是 **Experiment（实验）**，它连接任务、版本化配置、运行、干预和评价。六个模块是不同入口和视图。

| 模块 | 用户动作 | 共用的数据 | 首版体现 | 后续扩展 |
| --- | --- | --- | --- | --- |
| Learn | 阅读问题，预测结果，按引导做实验 | 场景、步骤说明、真实运行 | 两个实验中的内嵌讲解 | ReAct、RAG、Memory、MCP、多 Agent 课程 |
| Playground | 配置并运行 | 任务、Agent 版本、Run | 主工作台；一个 ReAct 模板 | 更多模板、模型和工具 |
| Builder | 改变结构或参数 | AgentDefinition、工具 schema | 参数表单和只读结构图 | 有限节点集合的可视化编辑器 |
| Debugger | 查输入输出、状态、错误，创建分支 | Span、Event、Checkpoint | 节点检查器、回放、允许边界的分支 | 断点、并行任务、子 Agent 调试 |
| Evaluation | 比较变体、复核评分 | Case、Variant、Score | 两次运行的对比与规则评价 | 数据集批跑、重复采样、统计分析 |
| Explore | 浏览和复用案例 | 实验包、模板、脱敏记录 | 随应用提供的案例库、文件导入导出 | 在线分享、社区贡献和检索 |

“都可以包含”体现在完整产品结构里。第一版把各模块需要的最小能力嵌入同一个工作台，以后的独立页面继续复用这些对象。

## 4. 第一个旗舰实验：工具超时以后发生了什么

### 任务与可控环境

任务示例：“根据给定的三份发布说明，整理两个版本的功能差异，并标出来源。”

使用随实验包提供的虚构发布说明，文件内容、版本和哈希固定；工具为 `search_documents` 与 `read_document`。它们运行真实检索代码，但数据源是实验夹具，不宣传成实时网页搜索。Agent 的模型请求在实时模式下使用真实模型提供商。

### 用户操作顺序

1. 打开场景，看到任务、成功标准，以及“首次检索将超时”的实验条件。
2. 先预测：失败后应该停止、重试，还是换一种策略？初学者可看简短说明。
3. 运行基线 A：选定工具调用首次超时，执行器配置为不重试，并按场景约定终止该次运行。
4. 在时间线上点击失败步骤，查看工具参数、超时事件、当时状态、错误来自哪一层。
5. 在工具执行前的有效 checkpoint 创建 B，将 `tool_retry_limit` 从 0 改为 1。其余任务、模型参数、工具数据、故障计划保持相同。
6. B 对该逻辑调用的第一次工具尝试仍按同一故障规则超时，第二次尝试才读取文档。这样比较的是重试配置，不是无意间取消了故障。
7. 对比 A/B：终止状态、工具尝试次数、是否取得材料、最终回答与引用、实际用量和新增耗时。
8. 解释当前证据：此实验验证执行器重试对瞬时故障的帮助；不能据此声称模型自己学会了恢复，也不能保证生成内容正确。

如果实时模型未选择目标工具，界面显示“故障条件未触发”，本次不纳入对应故障对比。不能伪造一次工具调用来配合教学。

### 为什么选择这个实验

它的失败来源明确，修改因素单一，恢复边界清楚，并同时需要实时记录、节点检查、状态快照、分支、指标和解释。完成它就能验证核心架构是否支撑产品愿景。

## 5. 第二个实验：没有检索到，还是没有正确使用

复用同一工具与文档结构，配置一个固定检索结果排序。基线 `top_k=2` 时缺少任务必需的第三份材料，候选 `top_k=3` 时才包含。

这里的 `top_k` 是工具执行器的检索配置，模型提供查询文本。分支只改该配置；详情同时显示查询与有效检索配置，避免把人工干预误写成模型自行改变了工具参数。

用户在检索前 checkpoint 改变 `top_k`，查看新增材料怎样进入后续上下文。评分分为两个层次：

- 过程检查：必需文档是否返回、是否成功读取、回答引用是否来自可用文档。
- 结果检查：要求的事实是否覆盖；缺少证据时是否如实说明信息不足。

信息不足时如实回答，应视为合适行为，不能简单算作“模型失败”。获得正确文档后仍答错，才进一步检查证据使用。自由文本事实正确性需要人工复核或明确标记的模型评价，不能用字符串命中假装验证语义。

两个实验均需提供真实录制的参考记录。没有真实录制之前，设计示例只能标记为“合成示例”，不得显示成真实模型运行或真实 Token/成本。

## 6. 工作台与信息层级

建议桌面端优先，中文文案保留必要的技术标识。深浅色风格暂不作为本轮决策。

```text
┌ 场景 / 实验名     历史运行     回看记录 / 实时运行     运行状态 ┐
│ 任务与配置          执行过程                       步骤详情    │
│ ─────────          ────────                       ────────    │
│ 任务与成功标准      Agent / 工具 / 评价事件         输入 / 输出 │
│ Agent 模板          实际经过的路径                 状态 / 错误 │
│ 模型、工具参数      列表视图或图视图               用量 / 来源 │
│ 故障条件            当前步骤                      解释        │
│ 运行 / 取消         选中失败节点                  创建分支    │
├ 回放：上一步  播放/暂停  下一步  速度     时间线与事件筛选      ┤
│ 结果与对比：A/B 配置差异 | 输出 | 评价 | 过程 | 成本与延迟      │
└─────────────────────────────────────────────────────────────┘
```

关键交互规则：

- **先呈现一次运行的事实。** 节点显示类型、状态和简短结果；原始 JSON、模型请求、错误栈可展开。
- **引导开关只改变解释层。** 切换专业视图不丢失当前节点、配置和运行。
- **结构图与执行图分开。** 模板循环节点可能执行多次，每次有独立调用编号；不能把多次调用覆盖为一个结果。
- **列表也是完整入口。** 用户不用拖拽画布也能键盘定位步骤、阅读输入输出、创建分支。
- **播放暂停只暂停记录播放。** 实时任务单独提供取消；首版不把暂停动画伪装成暂停远端模型。
- **创建分支只出现在可恢复边界。** 普通导入记录仍能检查和回放，但说明缺少 checkpoint 或运行适配器。
- **输出、评价与解释分开。** 模型回答是输出；判分器结果是评价；教学注释是解释，三者都有来源标识。
- **对比先显示改动。** 用户先看到什么参数不同，再看指标，避免把多处配置变化归因于单个参数。

窄屏改为任务、过程、详情的标签页。图中状态除颜色外还应有图标和文字，支持减少动画、键盘导航和可读焦点。

## 7. 第一版范围与后续发展

### v0.1：完整实验闭环

- 一个真实可执行的 ReAct 模板；两个文档工具；一个真实模型适配器。
- 两个上述预设实验，允许修改任务文本和受支持参数。
- 实时事件、步骤输入输出、错误与重试、历史运行、记录回放。
- 在支持的串行 checkpoint 创建新分支，原记录保留。
- 两次运行的配置、轨迹、输出与指标对比；规则评价与人工复核标签。
- 引导式说明、真实参考记录播放、实验与记录文件导出/导入。
- 单用户本地运行；参考案例可离线回看；实时模型凭据由服务端配置。

录制参考案例前需要可用模型账户。当前环境没有声明就绪的模型凭据，本轮只完成设计；不能把样例文件或接口规划当成真实执行已验证。

### 核心验证后逐步增加

| 阶段 | 能力 | 进入条件 |
| --- | --- | --- |
| 下一阶段 | Plan-and-Execute、数据集批跑、重复采样、两个架构对照 | 同一实验的记录与评分可靠，可复跑 |
| 再下一阶段 | 有限节点 Builder、RAG 专项、故障类型扩充 | 模板配置和运行语义稳定，有结构编辑需求 |
| 后续 | 多 Agent 泳道、SDK/OTel 适配、Memory/MCP 实验 | 因果关系和能力协商已能表达并行与外部框架 |
| 社区阶段 | Explore 在线分享、贡献规范、实验集合 | 有值得复用的内容，并完成分享数据范围设计 |

这些是按依赖排序的方向，不是已经承诺的发布日期。Time Machine 进入首版的回放与分支；Failure Lab 从两个实验起步；Battle Arena 随批量评测和重复采样成长。

## 8. 验收标准

| 编号 | 可验证的标准 |
| --- | --- |
| P01 | 实时运行能显示实际模型与工具事件，最终状态与后端一致；未知 Token/价格显示未知 |
| P02 | 同一节点重复调用保留独立输入输出和状态；工具失败后能追溯到所属模型调用 |
| P03 | 一次运行结束后，回看其任意已记录步骤不再调用模型或工具 |
| P04 | 从有效 checkpoint 创建 B，A 不变；配置差异、父运行、分支点可见 |
| P05 | 超时实验 A/B 使用相同的首次故障规则；重试属于执行器还是 Agent 行动标注准确 |
| P06 | 文档实验分别显示证据可用性与答案评价；信息不足时的诚实回答不误判为编造 |
| P07 | 单次结果只标记为个例；样本数、缺失值、取消或基础设施错误不会被隐藏 |
| P08 | 导入普通 trace 能查看内容；不能恢复时不提供可用的运行分支操作 |
| P09 | 取消后真实在途调用如无法中断，显示取消请求状态，保留最终收到的用量和结果 |
| P10 | 无凭据时可以回看参考记录，实时运行明确显示尚未配置；导出包不包含凭据 |

这些是待实现的验收要求，尚未执行测试。

## 9. 如何判断值得继续扩展

主指标建议是**完成一次有证据的诊断与修改的用户比例**：能指出失败步骤，说明改变了哪个因素，运行后正确解释结果及限制。

第一轮可用性目标设为：5 位试用者中至少 4 位无需作者代操作完成一个场景；多数人能区分回放和重新执行，并且不会把缺失数据理解为零成本。它们是预设的产品门槛，不是实测成绩，也不具统计代表性。

同时记录首次成功运行时间、诊断耗时、错误归因、第二次实验是否复用、开发者接入额外成本。若用户只看动画而无法解释结果，应先改善说明和证据结构；若 Studio/Phoenix 已能同样轻松完成，则调整为可复用的实验模板或适配层。
