## 已核对的依据

- [DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)：当前请求参数表未列出 parallel_tool_calls；auto 可返回文本或一个以上工具调用，指定工具只约束工具名称。文档没有提供可据此保证“每响应至多一个调用”的开关。这里不能从“未列出”推断服务端一定拒绝或忽略该参数，也不能把 OpenAI 同名参数的保证套用过来。
- [DeepSeek Responses API 兼容说明](https://api-docs.deepseek.com/guides/responses_api/)：明确说明 parallel_tool_calls 被忽略，工具并行生成始终开启。这是另一个接口的说明；它支持“不应改用 Responses API 来解决本问题”的判断，不等于对 Chat Completions 做了服务端实测。
- [现有真实观察](../examples/m4/deepseek-document-live-observed.json)：B 一次返回两个 read_document 意图，既有 v1 在执行前拒绝，保存 695 Token，没有读取任一正文。已有提示要求一次最多一个工具，仍不能保证提供商遵循。

因此，本次不添加未经证实的请求参数，不通过降低温度、反复采样或换提示后挑选成功输出宣称修复。已有 6 次/4172 Token 保持原口径，费用和实际账单未知。

## 推荐方案：独立 v2，按响应顺序串行执行工具

这是一个**已获用户确认的执行语义变更**，不是对旧失败记录的修正。拟新增 document-react:2、对应提示和实验定义版本；v1 的提示、解析器、图状态、checkpoint 与既有实验包继续保持原语义。旧点只能交给旧执行器，不迁移为 v2。

v2 接受一次响应中的多个工具意图，但执行仍在同一运行内逐项串行：

1. 在执行任何一项之前，校验整批工具名称、参数结构、严格 index 类型、唯一 call ID 和总预算。批中有非法项则整批不执行，原响应及 usage 保留。
2. 仅使用现有 search_documents/read_document 两个本地只读工具；正文白名单在每项执行时校验。某项失败或取消后，不执行剩余项，不把未执行意图记成工具成功。
3. 每项分别记录工具 span、逻辑 call ID、调用编号和工具前 checkpoint。模型消息保留整个原始意图序列，工具结果按原序追加；全部结果齐备后才再次请求模型。
4. 保留最多 8 次模型调用，并明确限定最多 7 次逻辑工具执行；多意图不能把一次模型响应伪装成一个工具来绕过总预算。当前实验 retry=0。
5. 首次检索前、尚未执行工具时，才允许 top_k 单变量分支。完整消息、整批待执行意图及当前位置进入 checkpoint；分支只改策略和派生 Variant 元数据，保留原意图/顺序/调用身份和前缀。其他观察点不授予分支能力。
6. 评价仍分别检查材料返回、实际正文读取和引用来源；答案语义/人工标签独立。A/B 必须采用同一 v2 定义，不能将旧 v1 A 与新 v2 B 当作只改 top_k 的对照。

产品任务、材料、工具能力、单变量原则、只读导入和 P06–P10 验收条件不变。影响集中于版本选择、执行器/检查点、上下文校验、包定义与前端已知模板识别；需要新版本离线回归后再进行一次有界真实 A/B。既有两次失败和旧参考包单独保留，新的用量另列。

## 验证与推进顺序

既有 SDK 请求参数冻结已补强：记录工具定义、选择方式和实际发送的并行控制等静态参数；旧记录从已经保存的首次模型请求核对，不改写 RunConfig/事件/checkpoint。请求配置漂移在产生新分支或调用模型之前拒绝；执行器启动时再次检查，覆盖预检与排队后配置不同的情况。详见[运行服务](runtime-service.md)。这一项不改变工具执行语义，与 v2 的实现独立。

v2 实现后，离线验证整批预检、实际串行顺序、逐工具预算/取消/失败、同响应 call ID 去重、首检索分支、连续/并发分支、旧 v1 拒绝行为与原历史不变、完整导入导出/只读浏览器。只有有具体代码修复且这些验证通过后才新增真实请求；不保证新真实样本一定成功，实际结果和失败同样保存。

另一条路线是保持 v1，并接入另一个具有明确单调用约束且已配置的提供商；当前环境只配置了 DeepSeek。仅凭 OpenAI SDK 可以接收该参数，不能证明某个具体服务或模型会执行它。

2026-10-18 用户在澄清自带 Agent 与现成 Agent 的区别后确认：“先把针对我们小 agent 这做完善了，再做这个现有 agent”。据此继续本方案，不再重复请求执行边界确认；现成 Agent 接入待自带闭环完善后验证。

通用的是运行记录、事件、检查、历史回放、来源、对比和文件流转的基础协议/界面。答案评价器、配置编辑器和执行控制仍有模板/适配器边界：暂停、恢复、状态修改、分支、取消的具体语义须声明并验证，不承诺换对象后全部自动可用。逐步将模板相关逻辑放在适配边界，外部记录本身不授予执行权限。
